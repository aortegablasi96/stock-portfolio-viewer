# 0035. One labelled control: explicit `htmlFor`, an id the field owns, and no size axis

- **Status:** Accepted — **amended 2026-08-21 by Story #234**
- **Date:** 2026-08-01

> **Amendment (Story #234, [[0075-sidebar-nav-rhythm-and-the-boxed-currency]]).** The
> display-currency field in the sidebar's footer becomes a **boxed chip** on `--surface-raised`,
> and the `<select>` inside it gives up **two** properties this record had reserved to `.control`:
> its resting `border-color` (set to `transparent`, never `border: none`, so the metrics hold and
> `.control:hover:not(:disabled)` still wins on specificity to bring the accent edge back) and its
> `padding-inline` (zeroed, because the box already insets and a second inset misaligns the value
> against its own label). A bordered control inside a bordered box is two nested rounded rectangles
> in a 220px column.
>
> Everything else here stands, in that placement and every other: the generated id and the absent
> `id` prop, the shared ink, the `:disabled` treatment, the single focus ring, and `kind` as the
> only axis. The amendment is **one placement and two properties**, asserted in
> `sidebarRail.test.ts` rather than left to the diff — including that `color`, `font-size` and
> `background` are *not* re-declared there.

## Context

The Epic #125 audit found one class doing the work of a form-control family. `.select-control`
styled both the display-currency `<select>` and the two `<input type="date">` elements in the
custom range picker, and `.field-inline` wrapped the label for both — but the two call sites
labelled their controls **two different ways**:

| | `CurrencySelector` | `RangeFilter` |
| --- | --- | --- |
| Technique | `<label htmlFor>` + `id` | `<label>` wrapping a bare `<span>` |
| Id | `id="display-currency"`, a prop with a default | none |
| Label rule | `.field-inline label` | `.range-custom .field-inline span` |

Both techniques are valid HTML. Having both is what cost something: the second CSS rule exists
*only* because the label text sat in a `<span>` where the other used a `<label>`, so the first
rule could not reach it. A duplicate declaration with no design intent behind it — precisely the
drift [[0031-design-token-scales]] was opened to stop.

`.select-control` had two further gaps. It declared **no hover state** at all, so a control gave
no feedback where a button beside it did, and its disabled treatment was a hand-written copy of
`.btn:disabled` — the same two declarations, free to drift. Its `:focus-visible` rule was a
third copy, of the base ring this Epic had already made automatic.

## Decision

**One `Field` owning the label pairing, and one `.control` box shared by `Select` and
`DateInput`.**

### Explicit `htmlFor`, with the id generated by `Field`

The wrapping-`<label>` technique is the smaller change and was rejected. `Field` uses
`useId()` and pairs an explicit `htmlFor`, because **the id cannot safely be a name any call
site picks**: analytics tabs mount on first visit and then stay mounted
([[0027-analytics-views-persist-and-explicit-refresh]]), so the three views carrying a
`RangeFilter` — Performance, Dividends, Trade history — can all be in the document at once. A
defaulted id like `display-currency`, or a literal `range-from`, would then appear two or three
times over, and a duplicate id does not fail loudly: every label silently resolves to whichever
control the document holds first, leaving the rest unnamed.

`CurrencySelector` therefore loses its `id` prop. Identity is the field's, not the caller's.

The control is passed as **a function of that id** rather than as plain children, so a call site
cannot take the id and forget to apply it. The label names the control it sits beside by
construction, which is what "one labelling technique" has to mean to be worth having.

### The control has no size axis

The button and the card take `variant` × `size`. Both of this app's form controls are the same
dense box, so a size scale would ship with exactly one value in use — the call
[[0034-stat-tile-primitive-tone-axis]] already made for the tile, and the speculative
abstraction the project's principles rule out. What genuinely differs between the two controls
is **which native element they are**, so `kind` (`select | date`) is the only axis, and it
carries cursor and colour-scheme only: a select is clicked, a date input's text is edited in
place, and only the date input has a browser-supplied picker whose calendar glyph needs
`color-scheme` to know the surface under it is dark.

### Hover, disabled and focus are the button's, not the control's

`.control:hover:not(:disabled)` is `.btn-outline`'s hover, declaration for declaration, so a
control and a button beside it answer the pointer identically. `.control:disabled` is
`.btn:disabled`. `lib/fieldVariants.test.ts` compares both rule bodies and fails if either
drifts. No focus rule is declared at all — the zero-specificity base rule supplies it, which is
how `.select-control:focus-visible` deletes without losing its ring.

### The native `<select>` stays

Explicitly, as the story scoped it: a short static list of currency codes is what the platform
control is for, and it is correct on every input method with no dependency, no popup layer and
no keyboard handling of ours to keep accessible.

## Consequences

- **`Field` + `Select` / `DateInput` are the one way to show a labelled control.** Three rules
  are deleted — `.field-inline` (and its `label` descendant), `.select-control` (with its
  disabled and focus copies) and `.range-custom input[type='date']` — and the orphan
  `.range-custom .field-inline span` disappears with the technique that required it.
- **`DateInput` fixes `type` rather than defaulting it**, one step firmer than `Button`'s
  `type="button"`. A different type would silently strip the meaning from the `min`/`max` the
  caller still supplies, and those bounds are what stop the picker offering a day the imported
  history does not cover ([[0017-analytics-table-time-range-filter]]).
- **No layout shift anywhere.** Both builds were measured element by element against `main` in
  a harness carrying each build's own stylesheet and markup. Every height is unchanged — field
  32px, date input 32.4px, the actions column 104.8px, the range bar 32.4px — because the
  padding rounding onto `--control-pad-sm` (5.6/9.6px → 6/12px) is offset exactly by the type
  rounding onto `--text-xs` (13.6px → 12.8px). Only control *widths* move: the currency select
  +3.2px, each date input −3.2px, the custom range group −9px. Nothing below either control
  moves by a pixel, which is a better outcome than [[0034-stat-tile-primitive-tone-axis]]'s
  deliberate 7px.
- **One deliberate correction:** the controls gain the hover state they never had.
- **`--text-xs` rather than `--text-sm`** for both the label and the control, though 0.85rem sat
  midway between them. It is the size the date inputs' neighbouring preset chips already use
  (0.82rem, and `--text-xs` once #131 converts them), so the two round *together* rather than
  apart.

## Alternatives Considered

### Wrapping `<label>` around the control

No id, no `useId`, and `RangeFilter` already worked this way. Rejected because the accessible
name is then the label element's whole text content: the moment a field carries a hint, a unit
or a suffix beside the control, that text joins the control's name silently. The explicit
pairing also extends to `aria-describedby` if a hint is ever added, which the wrapping form does
not.

### An `id` prop, required rather than defaulted

Would have kept `Field` free of `useId`. Rejected: it makes every call site responsible for an
invariant it cannot see — uniqueness across *simultaneously mounted views* — and the failure is
silent. Requiring a prop that only breaks when a second copy of an unrelated view is open is not
a contract a caller can honour.

### `size` on the control, mirroring `Button`

Rejected as speculative, per the project's development principles. Both call sites want the same
box, and `--control-pad-sm` is one line to add to `.control` when a second size is genuinely
needed.
